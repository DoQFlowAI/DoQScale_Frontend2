# DoQFlow AI 프론트엔드 전체 구현 가이드

이 베이스에서 출발해 세 사람이 프론트엔드를 완성하기 위한 공통 안내입니다. 누가 어느 파일을 맡는지는 `ROLES.md`(01 계획서 기준), 단계별 방법은 사람별 가이드를 봅니다.

- 기준 문서: `DoqFlowAI_06_Frontend개발명세서_v1.3.md`(이하 명세), `DoQFlowAI_04_API설계서_v1.4.md`, `DoqFlowAI_03_데이터베이스설계서.docx`
- 문서와 Figma가 다르면 문서를 따릅니다.
- 이 가이드에서 "명세 4.4"처럼 쓴 것은 FE 명세서의 절 번호입니다.

## 1. 전체 그림

### 화면

| 경로 | 페이지 | 소유 | 내용 |
|------|--------|------|------|
| `/login` | LoginPage | KJH | 로그인 |
| `/signup` | SignupPage | KJH | 회원가입 (직급 선택, 팀장 인증키) |
| `/` | DashboardPage | WJH | 질의응답 |
| `/documents/:documentId` | DocumentDetailPage | JJW | 버전 목록, 버전 정보·본문 사이드 패널(필수, Backend·산출물 반영 대기, 10장), 변천사, 업로드(WJH 부품), 열람자(KJH 부품), 정보 수정·삭제, 챗봇(WJH 부품) |
| `/documents/:documentId/compare?from=&to=` | CompareResultPage | JJW | 두 버전 좌우 비교 |
| `*` | NotFoundPage, ErrorPage | 베이스 | 없는 경로, 렌더링 오류 |

Header(초대 알림)와 Sidebar(문서 목록, 문서 만들기)는 로그인 후 모든 화면에 보입니다. 틀은 WJH, 안에 들어가는 초대 알림·문서 목록·문서 만들기는 KJH입니다.

### 요청 흐름

```
컴포넌트·페이지 → services/*Service.js → services/api.js (토큰 첨부, 응답 정리, 401이면 tokenRefresh.js)
  → /api/...  → 로컬: Vite 프록시 → 목 서버(:8080) 또는 실제 Backend
              → 배포: Nginx → Backend
```

- 화면 코드는 목 서버와 실제 Backend를 구분하지 않습니다. 바꿀 때 코드를 고치지 않습니다.
- AI 모듈을 직접 부르지 않습니다. 질의응답도 Backend의 `/ai/chat`을 거칩니다.

## 3. 베이스가 주는 것 (사용법)

### API 호출

```js
import { documentService } from '../services/documentService';
import { getErrorMessage, isNotFound } from '../utils/errors';

try {
  const doc = await documentService.get(id);   // 서버의 { success, data } 에서 data 만 옴
} catch (e) {
  setError(getErrorMessage(e));                // 500·502·네트워크는 고정 문구, 나머지는 서버 문구
  if (isNotFound(e)) { /* 없는 문서·권한 밖 문서 (구분하지 않음) */ }
}
```

| 서비스 | 함수 |
|--------|------|
| authService | `signup({email, password, name, rankLevel, signupKey})`, `login(email, password)`, `refresh(refreshToken)`, `logout(refreshToken)` |
| userService | `me()`, `lookup(email)` |
| invitationService | `list()`, `accept(permissionId)`, `reject(permissionId)` |
| documentService | `list({page, size, sort})`, `get(id)`, `create({name, description, inviteeEmails})`, `update(id, patch)`, `remove(id)`, `permissions(id)`, `invite(id, emails)`, `revoke(id, userUuid)` |
| versionService | `upload(id, files)`, `get(id, versionNo)`(버전 단건 + 본문 `contentText`, Backend 반영 대기), `remove(id, versionNo)`, `history(id)`, `compare(id, from, to)` |
| chatService (WJH) | `createSession()`, `messages(sessionId)`, `stream(...)`(WJH가 작성) |
| session | `expireSession()` — 로그인 상태와 대화를 모두 비움 |

- 오류는 모두 `ApiError { status, code, message, traceId }`로 옵니다. `status` 0은 네트워크 오류입니다.
- 401이 오면 `api.js`가 KJH의 `refreshAccessToken()`으로 갱신 후 한 번 다시 보냅니다. KJH가 완성하기 전에는 바로 로그아웃됩니다(목 서버 토큰 수명이 하루라 개발 중에는 거의 일어나지 않음).

### 상태

| 스토어 | 내용 |
|--------|------|
| `useAuthStore` | `user`(`uuid, email, name, rankLevel, createdAt`), `accessToken`, `refreshToken`, `isAuthenticated` / `login`, `logout`, `setTokens`, `setUser` |
| `useChatStore` | `sessionId`, `messages`, `isLoading` / `setSession`, `setMessages`, `addMessage`, `appendToken`, `finishMessage`, `clear` |

- 팀장 여부: `useAuthStore((s) => s.user?.rankLevel === LEADER_RANK)` (`utils/format`의 `LEADER_RANK`)
- 서버 데이터(문서, 버전 등)는 store에 두지 않고 페이지 state에 둡니다 (명세 5.4).
- 사이드바 목록을 다시 받아야 하면 페이지에서 `const { refreshDocuments } = useOutletContext();`

### 공통 컴포넌트

| 컴포넌트 | 주요 props |
|----------|-----------|
| Button | `variant`(primary·outline·danger·ghost), `size`(md·sm), 나머지는 button 속성 |
| TextField | `label`(필수), `error`, `hint`, 나머지는 input 속성 |
| Modal | `open`, `title`, `subtitle`, `onClose`, `footer`, `width`, `closeDisabled` |
| ConfirmDialog | `open`, `message`, `onConfirm`, `onCancel`, `pending`, `confirmLabel` |
| Chip | `tone`(green·soft·white·warn·danger·gray), `size`(sm·md) |
| StatusBadge | `status` (EMPTY·PROCESSING·READY·FAILED·PENDING·ACCEPTED·REJECTED → 한글 문구·색) |
| RankBadge | `rankLevel` (1 사원, 2 팀장) |
| LoadingSpinner | `label` |
| ErrorMessage | `message`(필수), `traceId`, `onRetry` |
| PageError | 화면 전체 오류 + 대시보드 링크. `message`, `traceId`, `onRetry` |
| Card | 흰 카드 섹션. `title`, `actions`(제목 오른쪽 버튼), `className` |

### 디자인 토큰 (`src/index.css`)

## 4. 코딩 규칙

1. 자기 소유 파일만 고칩니다. 다른 사람 파일이 필요하면 소유자에게 요청합니다.
2. API 호출은 서비스 함수로만 합니다. 컴포넌트는 데이터를 props로 받고, 사용자 동작은 `onXxx` 콜백으로 올립니다 (명세 5.4).
3. 모든 컴포넌트에 `propTypes`를 씁니다 (명세 5.1, lint가 검사합니다).
4. 데이터 화면은 로딩·정상·빈 결과·에러 4가지 상태를 모두 그립니다 (명세 4.3). 빈 결과 문구에 권한 밖 문서가 있다는 암시를 넣지 않습니다.
5. 권한 없음과 문서 없음을 화면에서 구분하지 않습니다 (서버가 둘 다 404).
6. 버튼 숨김은 편의 기능입니다. 최종 판단은 서버가 하므로 요청에 직급·사용자 식별자를 넣지 않습니다 (회원가입 `rankLevel` 예외).
7. 보안: `dangerouslySetInnerHTML` 금지. AI 답변, 인용 조각, 문서·파일·사용자 이름, 비교 본문은 텍스트로만 그립니다. 토큰·인증키·질문 원문을 `console.log`에 남기지 않습니다.
8. 모바일 390px에서 가로 스크롤이 없어야 하고, 누르는 영역은 44px 이상(`min-h-11`)입니다 (명세 8.1).
9. 가짜 데이터는 컴포넌트에 넣지 않고 목 서버에 넣습니다.

## 5. 담당 간 약속

다른 사람 화면에 들어가는 것은 아래 이름·props로 만듭니다. 끼우는 일은 화면 주인이 합니다. 바꿔야 하면 쓰는 쪽과 먼저 이야기하고 이 표를 고칩니다.

### KJH가 만들고 WJH가 끼움 (레이아웃)

| 이름 (KJH) | 약속 | 끼우는 곳 (WJH) |
|------------|------|-----------------|
| `utils/useDocumentList()` | 반환 `{ documents, hasMore, loading, error, loadMore, refresh }` | Layout. `refresh`를 Outlet context의 `refreshDocuments`로 내림 |
| `document/DocumentTabList` | `documents`(필수), `hasMore`, `loading`, `error`, `onLoadMore`, `onRetry` | Sidebar. 위 반환값을 그대로 연결 |
| `document/DocumentCreateModal` | `open`(필수), `onClose`(필수), `onCreated(documentId, flash)`(필수) | Sidebar. 팀장에게만 [문서 만들기]. `onCreated`를 받으면 모달 닫기 → `refresh()` → `navigate('/documents/' + id, { state: { flash } })` |
| `common/InvitationMenu` | `onAccepted` | Header. 수락하면 `refreshDocuments()` |

`flash`는 `{ notice?, error? }` 형태의 안내 문구입니다(예: 업로드 실패, 가입되지 않은 이메일). JJW의 문서 상세가 `location.state.flash`로 읽어 한 번 보여 줍니다.

### KJH·WJH가 만들고 JJW가 끼움 (문서 상세)

| 이름 | 만드는 사람 | 약속 |
|------|-------------|------|
| `document/PermissionPanel` | KJH | `documentId`(필수), `owned`(필수), `uploadedByName`, `onClose`(필수). 열람자 목록·초대·회수를 하는 모달. 열고 닫는 상태는 JJW |
| `common/VersionUploadPanel` | WJH | `files`(필수), `onChange(files)`(필수), `startVersionNo`(필수), `disabled`. 파일 고르기·순서·검증만 하고 전송은 하지 않음 |
| `chat/ChatWidget` | WJH | props 없음. 문서 상세 맨 끝에 한 번 |

JJW는 업로드 영역을 자기 `VersionTable`의 `children` 자리에 두고, [올리기]와 `versionService.upload` 호출은 직접 합니다.

### WJH가 만들고 KJH가 끼움 (문서 만들기)

| 이름 (WJH) | 끼우는 곳 (KJH) |
|------------|-----------------|
| `common/VersionUploadPanel` (위와 같은 props, `startVersionNo`는 1) | DocumentCreateModal의 첫 버전 파일 |

### 함수·상태

| 주는 쪽 | 받는 쪽 | 약속 |
|---------|---------|------|
| KJH `services/tokenRefresh.js`의 `refreshAccessToken()` | 베이스 `api.js`, WJH `chatService.stream` | 성공하면 새 accessToken 반환, 실패하면 throw. 이름 유지 |
| WJH `chatStore`의 `clear()` | KJH LoginPage, 베이스 `session.js` | 대화를 모두 비움. 이름 유지 (이미 연결됨) |
| WJH Layout의 Outlet context `{ refreshDocuments }` | JJW 페이지 | 생성·수정·삭제·업로드·폴링 뒤 사이드바 갱신 |

연동 전에는 상대 컴포넌트 자리에 `{/* KJH: PermissionPanel */}`처럼 주석만 두고 개발합니다. 자기 컴포넌트는 미리보기에서 확인합니다(6장).

## 6. 혼자 확인하는 방법

### 매번 로그인이 필요한 경우

새로고침(F5)하거나 주소창에 주소를 직접 입력하면 로그인이 풀립니다. 토큰을 메모리에만 두기 때문이며(명세 9.2), 버그가 아닙니다.

- 다시 로그인하면 처음 입력한 주소로 돌아갑니다 (`ProtectedRoute`가 원래 주소를 기억하고 `PublicOnlyRoute`가 돌려보냄).
- 코드를 저장할 때(Vite 화면 갱신)는 풀리지 않습니다.
- 계속 로그인 상태로 확인하려면 화면 안의 링크·버튼(`Link`, `navigate`)으로 이동합니다. 아직 링크가 없는 화면은 내 `LocalPreview.jsx`(아래 미리보기)에 임시 링크를 둡니다.
- 개발 편의를 위해 토큰을 localStorage·sessionStorage에 저장하지 않습니다. 보안 점검(명세 9.2) 대상입니다.

### 목 서버

`npm run mock`이면 API 설계서의 전체 API가 고정 데이터로 동작합니다. 토큰 수명은 기본 하루라 개발 중에는 만료되지 않습니다(갱신 확인은 KJH 가이드 참고). 계정과 문서별 상황은 README의 "테스트 계정" 절에 있습니다.

- 목 서버에 필요한 동작이 없으면 WJH에게 요청합니다.
- Windows 터미널 curl로 한글이 든 요청을 보내면 글자가 깨집니다. 브라우저 화면이나 Node로 확인합니다.

### 미리보기 (`/preview`)

미리보기는 세 사람이 서로의 작업이 끝나기를 기다리지 않고 동시에 개발하기 위한 개인 연습장 화면입니다. 내가 만든 컴포넌트를 내 PC에서 나 혼자 띄워 봅니다. 남을 위해 무언가를 고치는 곳이 아닙니다.

왜 필요한가: 만드는 사람과 그 컴포넌트가 들어갈 화면의 주인이 다른 경우가 많습니다. 예를 들어 WJH가 만드는 `ChatWidget`은 JJW의 문서 상세 화면에 들어갑니다. 문서 상세는 JJW 파일이라 WJH가 고칠 수 없고, JJW가 화면을 완성하기 전에는 WJH가 자기 챗봇을 볼 곳이 없습니다. 미리보기에 올려놓으면 기다리지 않고 바로 만들고 확인할 수 있습니다.

쓰는 방법

1. 내 PC에 `src/preview/LocalPreview.jsx`를 만든다 (처음 한 번)
2. 확인할 내 컴포넌트를 넣는다
3. `npm run dev` → 로그인 → 주소창에 `/preview` (주소 입력이라 다시 로그인하면 이 화면으로 돌아옴)

흐름 (WJH의 ChatWidget 예)

1. WJH가 `ChatWidget`을 만든다 (WJH 파일)
2. 자기 PC의 `LocalPreview.jsx`에 `<ChatWidget />`을 올리고 `/preview`에서 확인한다
3. 완성되면 JJW에게 알린다
4. JJW가 자기 문서 상세 화면에 끼운다 (JJW 파일)

비유하면 남의 방에 놓을 가구를 내 방에서 먼저 조립해 보는 것입니다. 다 조립되면 방 주인에게 넘기고, 어디에 놓을지는 방 주인이 정합니다.

| 사람 | 주로 올려 볼 것 (다른 사람 화면에 들어가는 것) |
|------|-----------------------------------------------|
| KJH | `InvitationMenu`, `DocumentTabList`, `DocumentCreateModal` (WJH 레이아웃용), `PermissionPanel` (JJW 상세용) |
| JJW | `VersionTable`, `HistoryTimeline`, `VersionSelectModal`, `DiffViewer` (상세 화면 완성 전), 비교 주소로 가는 임시 링크 |
| WJH | `ChatWidget`, `VersionUploadPanel` (JJW 상세·KJH 모달용) |

그 밖의 쓰임

- 임시 링크 모음: 주소창에 직접 입력하면 다시 로그인해야 하므로, 자주 가는 주소를 `Link`로 모아 두고 눌러서 이동하면 로그인이 유지됩니다.
- 상황별 비교: 같은 컴포넌트를 props만 바꿔 여러 개 띄울 수 있습니다(예: 등록자용과 열람자용 `PermissionPanel`을 나란히).

지킬 것

- `LocalPreview.jsx`는 `.gitignore`에 있어 git에 올라가지 않습니다. 각자 PC에만 있고 내용도 사람마다 다릅니다. 그래서 충돌도, develop에 시험 코드가 쌓이는 일도 없습니다.
- 파일이 없으면 `/preview`에 만드는 방법 안내만 나오고 오류는 나지 않습니다.
- `npm run dev`에서만 열리고 배포 빌드에는 들어가지 않습니다.
- 내가 만든 것만 올립니다. 남의 파일은 건드리지 않습니다.
- 미리보기에서 잘 된 것으로 끝나지 않습니다. 연동한 뒤 실제 화면에서 다시 확인합니다.

```jsx
// src/preview/LocalPreview.jsx 예시 (JJW)
import { useEffect, useState } from 'react';
import LoadingSpinner from '../components/common/LoadingSpinner';
import VersionTable from '../components/document/VersionTable';
import { documentService } from '../services/documentService';

export default function LocalPreview() {
  const [doc, setDoc] = useState(null);
  useEffect(() => { documentService.get(1).then(setDoc); }, []);
  if (!doc) return <LoadingSpinner />;
  return <VersionTable versions={doc.versions} currentVersionNo={doc.currentVersionNo} owned={doc.owned} onDelete={() => {}} />;
}
```

## 8. Git 작업 방식

```sh
git switch 내브랜치            # KJH, JJW, WJH
git fetch origin
git merge origin/develop      # 작업 전·PR 전에 develop 따라가기
npm run lint && npm run build
git add 고친파일들              # git add . 대신 파일을 지정 (package-lock.json, .env 실수 방지)
git commit -m "feat: ..."
git push
```

- 본인 브랜치에서 작업하고 `develop`으로 PR을 올립니다.
- PR의 바뀐 파일 목록에 자기 소유가 아닌 파일이 있으면 빼거나 소유자와 이야기합니다.
- Node 20.19 이상 또는 22.12 이상을 씁니다(`package.json`의 `engines`). 낮으면 `npm run dev`에서 안내 메시지가 나옵니다.
- 줄바꿈은 `.gitattributes`가 커밋할 때 LF로 통일합니다. 한 줄만 고쳤는데 파일 전체가 바뀐 것으로 보이면 `git diff`로 줄바꿈 차이인지 먼저 확인합니다. 들여쓰기는 2칸입니다.
- `npm install`은 `package-lock.json`을 바꿀 수 있습니다. 평소에는 `npm ci`를 씁니다. 패키지를 새로 추가해야 하면 WJH와 먼저 이야기합니다.
